# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

BitNode Console is a web-based interface for managing a Bitcoin Knots/Core daemon
node — configuration (`bitcoin.conf`), status monitoring, and log viewing without
requiring CLI/SSH access. The project is in its **feasibility stage** (see
`docs/product-requirements.md` and the `README.md` roadmap): auth against a
configured Argon2id password hash, journalctl log viewing/following, and
daemon/config handling are being proven out. Expect parts of the product
requirements to be unimplemented.

## Architecture

Cargo workspace (`backend/bins/*`, `backend/libs/*`) plus a separate React SPA in
`frontend/`. Three server binaries compose the same libraries differently, each
with a near-identical `lib.rs::run()` (parse settings → init tracing → start servers):

- `bin_console` — HTTP (`lib_web`) **and** gRPC (`lib_rpc`) run concurrently via
  `tokio::try_join!`. Owns the integration tests (`tests/{backend,startup,web}`).
- `bin_backend` — gRPC only (headless / API-only).
- `bin_frontend` — HTTP only (SPA host).

Libraries:

- `lib_settings` — layered config: built-in defaults → system/user/exe-dir/cwd
  `bitnode_console.conf` → explicit file → env vars (`BITNODE_CONSOLE_*`) → CLI
  flags (`Cli`, highest precedence). Sections map to `ApplicationSettings`,
  `BitcoinDaemonSettings`, `BackendSettings`, `FrontendSettings`, `TracingSettings`.
  See `backend/libs/lib_settings/README.md`.
- `lib_rpc` — tonic gRPC server (with gRPC-Web + CORS layers and reflection).
  Services live in `src/services/{authentication,journals,utilities}`;
  `interceptors/` holds `AllowedIpsInterceptor` and `AccessTokenInterceptor`.
  The server refuses to start if `backend.password_hash` is empty.
- `lib_auth` — password hashing and `AccessToken` (signed with `token_secret`).
- `lib_journals` — reads/follows systemd journal entries (shells out to
  `journalctl`, so it needs systemd on the host); the data source for the logs page.
- `lib_core` — shared domain types. `lib_tracing` — tracing init.
- `lib_web` — axum `ServeDir` over `backend/libs/lib_web/assets/`, falling back to
  `index.html` for SPA routing.

### Cross-cutting things that span files

- **Protobuf is the frontend/backend contract.** `.proto` files live in
  `backend/libs/lib_rpc/protos/bitnode_console/*/`; `frontend/protos` is a
  symlink to that directory. The Rust side is generated at build time by
  `lib_rpc/build.rs` into `OUT_DIR` (not committed). **Adding a new `.proto`
  requires adding it to the explicit file list in `build.rs`** and to the
  `proto:gen` script in `frontend/package.json`. The TypeScript client is generated
  with `pnpm run proto:gen` into `frontend/src/lib/generated_protos`.
- **`lib_web/build.rs` runs `pnpm run build` in `frontend/`** on every Rust build
  where `frontend/src` changed, so `pnpm` and Node must be installed for
  `cargo build`/`cargo test` of any crate depending on `lib_web`. The built SPA
  must then be in `lib_web/assets/` (`mise run console-assets-copy` copies
  `frontend/dist` there).
- **Auth flow:** the browser logs in over gRPC-Web with the password, receives an
  access token, and sends it in an `access_token` metadata header on later calls;
  requests are also filtered by the allowed-IPs list.
- **Frontend** (`frontend/`): React 19 + Vite + TanStack Router (file-based routes
  in `src/routes`; `routeTree.gen.ts` is generated by `tsr generate`) + TanStack
  Query + shadcn/ui + Tailwind. Routes are split into `_public/` and `_restricted/`.

## Development Environment

Toolchain is pinned by `mise.toml` (Rust is further pinned by
`rust-toolchain.toml`). Run `mise install` from the repo root, then `mise tasks`
to list tasks. System libraries (openssl, pkg-config, argon2, systemd/journalctl)
come from the OS package manager. `mise.toml` replaced the old Nix/direnv and
cargo-make setup — don't reintroduce `Makefile.toml`/`shell.nix`.

For local development, `bitnode_console.conf` in the repo root is picked up from
the working directory and contains a dev password hash and token secret, and
`dev/run-bitcoind.sh` runs a regtest Knots daemon whose logs go to the journal
(`systemd-cat -t bitcoind`).

## Common Commands

- Build: `cargo build` (triggers the frontend build, see above)
- Run full server (web + gRPC): `cargo run -p bin_console`
- Run gRPC-only server: `cargo run -p bin_backend`
- Test (all): `cargo test`
- Test (single): `cargo test <test_name>`; integration test targets in
  `bin_console` are `--test backend`, `--test startup`, `--test web`
  (e.g. `cargo test -p bin_console --test backend journals`). Set `TEST_LOG=1`
  to see tracing output in integration tests.
- Lint / format: `cargo clippy`, `cargo fmt`
- Full dev loop with hot reload (builds frontend, starts regtest bitcoind,
  `cargo watch`): `mise run console-dev` or `mise run backend-dev`
- Frontend only: `mise run frontend-dev` (Vite), `mise run frontend-lint`
- Docs (mdBook, port 8001): `mise run docs-build` / `mise run docs-serve`
- Docker images (Dockerfiles in `docker/`, build context is the repo root):
  `mise run docker-build-all`

## Workspace Lint/Style Configuration

Lint rules are centralised in the root `Cargo.toml` under `[workspace.lints]`
and apply to all crates unless overridden locally:

- `unsafe_code = "forbid"` — no unsafe code anywhere in the workspace.
- `warnings = "deny"` — all compiler warnings are errors; code must compile cleanly.
- `unused = "allow"` (low priority) — permitted during exploratory development;
  clean up before committing where practical.
- `clippy::pedantic` and `clippy::nursery` are `warn`, with a long list of
  specific lints allowed in the root `Cargo.toml` — check there before
  "fixing" a lint.
- `rustfmt.toml`: max width 100, stable options only (edition 2024).

Shared dependency versions live in `[workspace.dependencies]` in the root
`Cargo.toml`; reference them with `{ workspace = true }` from member crates.

## Rust Coding Conventions

- Prefer `Result<T, E>` and `?` over `unwrap()`/`expect()`; avoid panics outside
  truly unrecoverable situations.
- Each crate has its own `Error` enum (`thiserror`) in `error.rs` and a
  `Result<T>` alias re-exported from `lib.rs`; follow that pattern.
- Prefer borrowing over cloning; prefer iterators over index loops.
- Keep `main.rs`/`lib.rs` minimal; split logic into modules and re-export.
- Document all public items with `///` rustdoc comments, written in
  Australian English.
- Use the `fake` crate for test data; unit tests go in `#[cfg(test)] mod tests`
  alongside the code, integration tests under `tests/`.
- Code must pass `cargo fmt`, `cargo clippy`, and `cargo test` before committing.

## Markdown Conventions

For `.md` files (docs are built with mdBook from `docs/SUMMARY.md`):

- Do not use an H1 (`#`) heading — titles are generated automatically; start at H2 (`##`).
- Include YAML front matter with required metadata where applicable.
- Use fenced code blocks with a language identifier.
- Wrap prose at roughly 80 characters.
